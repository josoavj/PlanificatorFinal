Architecture et modèle de données

Une application Flutter desktop structurée autour de repositories et d’un schéma MySQL partagé.

Organisation du code

lib/
├── core/          Initialisation, thème, requêtes SQL
├── models/        Modèles métier et conversion des données
├── repositories/  Règles métier et opérations SQL
├── services/      Connexion MySQL, cache, logs, sauvegardes
├── screens/       Parcours d’interface
└── utils/         Dates, validateurs et formateurs

Les widgets présentent les données et délèguent les opérations aux repositories. Les requêtes partagées sont centralisées dans lib/core/sql_queries.dart. DatabaseService gère la connexion, le pool et les transactions.

Relations métier principales

ÉlémentsRelation et usage
Client → ContratUn client peut avoir plusieurs contrats.
Contrat → TraitementLes traitements décrivent les services convenus dans le contrat.
Traitement → PlanningUn traitement génère un planning d’interventions.
Planning → PlanningDetailsLes détails portent les dates et états de chaque passage.
PlanningDetails ↔ FactureLa facture est reliée aux détails du planning ; des détails peuvent partager une facture groupée.
Historique, Remarque, SignalementConservent le suivi des événements et informations associés aux interventions.

Facturation et lien avec le contrat

La table Facture stocke notamment planning_detail_id et date_traitement. Elle ne stocke pas de colonne contrat_id, date_emission ou date_echeance. Une requête qui doit retrouver le contrat passe par PlanningDetails → Planning → Traitement → Contrat.

Les index du schéma sont définis dans scripts/Planificator.sql. La commande ANALYZE TABLE rafraîchit les statistiques utilisées par l’optimiseur SQL ; elle ne crée pas d’index.

Plateformes et technologies

  • Flutter desktop sur Windows, Linux et macOS.
  • Dart, Provider, MySQL via le package mysql1.
  • BCrypt pour le hachage des mots de passe.
  • Stockage sécurisé des identifiants de connexion.
  • Exports Excel et calendrier d’interventions.
